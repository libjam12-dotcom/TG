# Chatcleaner: исходники для доработки инвайтинга

Это отдельная очищенная копия для внешнего разработчика. Производственные учётные записи, базы, сессии, персональные списки, переписка, секреты, история Git и доступ к серверу отсутствуют. Идентификаторы и профили в коде/тестах заменены тестовыми. Личный модуль сообщества владельца заменён пустым адаптером; старый рекламный шаблон исключён. Остальные клиентские подсистемы включены для понимания зависимостей.

## Быстрый запуск

Нужны Python 3.12 и Node.js 20+ (Node нужен для тестов интерфейса). Выполнять из корня распакованного пакета:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r scanner/requirements.txt
.venv/bin/python dev/run.py
```

Открыть http://127.0.0.1:8080/#invite-settings . Порты 8080 и 8787 должны быть свободны. Остановить Ctrl+C. На Windows использовать `.venv\Scripts\python.exe` вместо `.venv/bin/python`.

Локальный адаптер заменяет производственный вход тестовой ролью владельца, проксирует API в backend на 127.0.0.1:8787 и НЕ является сервером авторизации для публикации в интернете. Входной Host и Origin проверяются. Интерфейс и backend слушают только loopback. Не публикуйте порты через туннели и не меняйте bind на 0.0.0.0.

Новая `.local-data/` создаётся только при запуске. Аккаунт не подключён, задания отсутствуют. Исходящий Python-трафик по умолчанию блокируется `dev/sitecustomize.py`, включая DNS вне localhost. Это защита от случайного обращения, а не полноценная песочница. Для изоляции используйте собственную VM/контейнер без доступов владельца. Не запускайте исходники в каталоге с настоящими сессиями.

Для настоящего теста разработчик использует СВОЙ выделенный аккаунт и СВОЮ закрытую группу с согласившимися участниками. После отдельного согласования он может установить `HANDOVER_ALLOW_EXTERNAL=1` перед запуском; тогда блокировка внешней сети снимается. API ID/hash получают самостоятельно через https://my.telegram.org/apps . Никаких общих реквизитов в пакете нет. Восстановление реального аккаунта/сессии из этого пакета невозможно.

# Инвайтинг: задача и фактическая диагностика

## Задача

Пользователь выбирает отправителя, управляемую группу и список согласившихся участников, задаёт предел попыток, интервал и необязательную цель подтверждённых добавлений. Сохранение черновика и просмотр страницы не должны приглашать людей. Явный запуск выполняет последовательные приглашения с видимым прогрессом; остановка и возобновление не повторяют уже обработанные/неизвестные результаты. Цель по числу участников не гарантирует, что Telegram разрешит добавления.

## Карта кода

- `manual-invite-campaign.js`: форма, валидация, quick-mode, состояние, polling и отображение причин.
- `scanner/manual_invite_campaign.py`: quick-draft/quick-start, разрешение username непосредственно перед обработкой, история, claim, единичный InviteToChannel, проверка членства, pause/stop.
- `scanner/operations.py`: аккаунты, общая очередь, общий outbound guard, resume, safe_rpc_metadata/invite_rpc_diagnosis и API.
- `scanner/owner_sender.py`: основной отправитель; нельзя смешивать с отдельной сессией secondary.
- `scanner/operation_workbench.py`: границы аккаунта, целей и согласия.
- `scanner/invite_progress.py`: подсчёт результатов.
- `scanner/{isolated_invite,isolated_contact_batch,isolated_invite_campaign,invite_run_budget}.py`: прежние конечные сценарии со специальными рамками. Не запускайте все контроллеры одновременно; часть исторических констант в этой копии заменена синтетическими. Эти модули не являются универсальной квотой Telegram.
- `scanner/spambot_check.py`: ограниченная диагностика официального бота. Ответ «ограничений нет» не доказывает успешность InviteToChannel.
- `scanner/tests/`, `tests/manual-invite-campaign.test.cjs`: unit/поведенческие проверки.

Объекты SQLite: op_accounts, op_jobs, op_items и settings manual_invite_campaign_job_*; активный ручной контроллер нельзя искать только по op_jobs.state. Журнал должен сохранять фазу, метод, безопасный RPC-код, время и outcome без телефонов, access_hash, auth_key и сырого request/exception текста.

## Наблюдавшиеся классы сбоев (без клиентских данных)

1. FLOOD_WAIT_X — Telegram требует паузу на X секунд. Истечение этой паузы само по себе не обещает успешность следующего приглашения.
2. PEER_FLOOD — получен непосредственно на InviteToChannel, в том числе в отдельной технической группе. Точного срока в самом ответе не было. Не следует объявлять это постоянным баном или «теневым баном группы» без доказательств.
3. UserNotMutualContactError и privacy/missing_invitees — ограничения конкретного приглашения. Нельзя распространять их на всех пользователей или считать взаимность универсальным требованием API.
4. Telegram вернул InvitedUsers без missing_invitees, но членство не подтвердилось. Такой результат нельзя считать успешным или молча повторять.
5. После окончания сохранённого FloodWait одна попытка основного отправителя закончилась BadRequestError. Поздняя проверка подтвердила отсутствие участника. Конкретное message потеряно общим except и не восстановилось из журнала. Нельзя приписывать этому случаю CHAT_MEMBER_ADD_FAILED без фактов.
6. Предварительная проверка большого списка задерживала реальные попытки и не давала понятного прогресса. Quick-mode уже существует: список разрешается по одному перед обработкой. Минимальная проверка отправителя/прав/членства нужна для корректного учёта, но не следует делать полный проход по всей базе перед первым инвайтом.

## Недавняя локальная правка

В общем except `ManualInviteCampaign.step`, если invitation уже заявлен, теперь добавляются `verification_error = invite_rpc_diagnosis(exc)` и `member_before`. Сохраняется прежний uncertain/stop/no-repeat. Безопасная metadata должна содержать SDK-класс, enum-код и конструктор метода; произвольный текст не сохраняется. `test_manual_rpc_regression.py` проверяет это на СИНТЕТИЧЕСКОМ CHAT_MEMBER_ADD_FAILED. Этот тест не раскрывает код потерянного реального ответа.

Требуется доработать: точное разделение фаз resolve/before-membership/invite/after-membership, известный отказ vs неизвестный результат; отрисовку сохранённой metadata; интеграционную приёмку. Не меняйте прошлую историю, чтобы сделать показатели красивее.

Официальная справка: https://core.telegram.org/method/channels.inviteToChannel , https://core.telegram.org/api/errors , https://telegram.org/faq_spam . Изучать с учётом установленного Telethon 1.40.0. Пакет не устанавливает квоту «50/100 в день» от имени Telegram.

# Критерии приёмки

1. Форма показывает ошибку возле конкретного поля и объясняет, что мешает продолжению. Учитывает sender identity, право приглашать, корректные/повторяющиеся username, согласие и пользовательские пределы.
2. Draft/GET/reload/переходы не выполняют приглашений, не снимают паузы и не возобновляют другие задания.
3. Quick-start не запускает предварительную проверку всей сотни; прогресс отражает реальные стадии и обновляется при ошибках API/перезагрузке страницы.
4. Перед сетевым действием сохраняется устойчивый claim; повторное нажатие/тайм-аут HTTP/перезапуск процесса не дублируют инвайт. Неизвестные результаты требуют ручного разбора.
5. Успех = до действия memberfalse, выполнено приглашение, после действия membertrue. Уже состоявшие, отказ, исключённые, попытки и uncertain считаются отдельно.
6. Сохраняются метод, фаза, безопасный RPC-enum и время; общий BadRequestError не скрывает доступный конкретный код. Текст ошибок не раскрывает request parameters, access_hash, session или proxy credentials.
7. FLOOD_WAIT соблюдается до серверного срока. PEER_FLOOD останавливает действия без повторов, смены аккаунта/прокси и сброса истории. Resume не обещает снятия ограничений Telegram и не включает старые очереди.
8. Pause/stop имеет понятный результат при текущем сетевом запросе; новое задание не запускается поверх другого контроллера того же аккаунта. Проверяются также settings контроллеров и общие бюджеты, не только последние задания.
9. Сохраняется привязка config_digest/telegram_id/target_id, устойчивость к смене аккаунта и адреса/ID группы. Изолированные тесты включают потерю ответа, reconnect, новые ограничения во время запроса, перезапуск и concurrent start.
10. Реальная приёмка — отдельная согласованная проверка со своим тестовым аккаунтом/группой и согласившимися участниками. Количество попыток оговаривается перед запуском; unit-тест не является подтверждением добавления в Telegram.
11. Сдача: патч относительно этого пакета, перечень файлов, команды/результаты тестов, безопасные примеры diagnosis, ограничения, инструкция миграции/отката. Не присылать рабочие sessions, tdata, базы и токены в репозиторий или чат.
12. Production не обновляется автоматически. Старые задания/история/аккаунты сохраняются; перенос только проверенных изменений, резервная копия и откат кода без уничтожения новых входящих данных.

# Происхождение и различия

Дата снимка: 29 октября 2026. Основа — локальная рабочая копия клиентской Telegram-панели. Это НЕ экспорт работающего сервера и НЕ новый production release.

Сопоставление с оригинальными ID разработчику не передаётся.

Очищены начальные бизнес-записи UI. Личный OwnerHub представлен пустым совместимым адаптером; NeuroVlad, изображения, контент сообщества, реальные логи, старые deploy/install/backup-скрипты, исходная README с историей, docs/evidence и Git не передавались. Клиентские операции и зависимости сохранены. Тесты личного OwnerHub исключены вместе с его содержимым.

Локальный репозиторий содержит изменения, которые ещё не установлены на сервере, включая дополнительные диагностические ветки и последнюю правку сохранения безопасной metadata при BadRequestError. Нельзя считать весь пакет побайтово соответствующим production или устанавливать его целиком. Требуется review конечного diff и перенос только относящихся к задаче изменений.

В полном приложении backend доверяет заголовкам, которые в production должен выставлять проверенный reverse proxy; нельзя выставлять Python backend напрямую в интернет.

Зависимости приложения зафиксированы в `scanner/requirements.txt`. `dev/constraints-tested.txt` содержит версии установленных прямых и основных транзитивных зависимостей из проверочной Python-среды, не универсальный lock для всех ОС. Подтверждено на Python 3.12; установка с нуля через pip в рамках этой передачи не выполнялась.

При сдаче обозначать: локальная реализация, автоматические тесты, проверка браузера и реальные добавления в Telegram — разные результаты. Производственные ошибки, чьи детали были утрачены, не восстанавливать предположениями.

# Передача и границы доступа

Пакет создан положительным списком файлов исходников, а не архивированием рабочей папки. Нет .git, .env, client-access, файлов ключей, cookies, runtime-баз, резервных копий, .session, tdata, списков контактов, фотографий, скриншотов, исходных отчётов или deployment-реквизитов. Никакой доступ не выдавался, репозиторий не опубликован, сервер не обновлялся.

Сессия Telegram эквивалентна доступу к аккаунту. Не просите у владельца основные sessions/tdata/2FA/Cloud/SSH. Для сетевого теста используйте свой тестовый аккаунт; приглашать можно только согласившихся участников, сохраняя реальные ограничения Telegram. Ограничения не обходить сменой аккаунта/прокси, сбросом cooldown или историей.

Запуск по умолчанию изолирован loopback и новой локальной базой. Блокировка внешних Python-сокетов уменьшает вероятность случайного действия, но не ограничивает произвольный код/дочерний процесс или браузер: для недоверенного кода нужна отдельная VM/контейнер и сетевые правила ОС. В среде разработчика не должно быть владельческих ключей и mounted production volumes. Не вводите реальные секреты в unit-тесты.

Перед первым коммитом запустите `python dev/audit_package.py` и изучите находки. Скрипт ищет запрещённые файлы, ключи, токены, production-домен и личные локальные пути, выполняет синтаксическую проверку Python и проверяет symlinks. Он не передаёт содержимое файлов в сеть. Совпадения тестовых паролей и ложных credentials в негативных unit-тестах классифицированы отдельно: они не дают доступ к сервисам. Автоматическая проверка не является математической гарантией отсутствия неизвестного секрета.

Передаваемый архив содержит только папку chatcleaner-developer. Внешние private-*.json, build-скрипты, локальные журналы и таблица исходных значений из рабочего каталога в архив НЕ входят. MANIFEST.sha256 позволяет проверить состав; контрольная сумма ZIP поставляется отдельно. Manifest не является цифровой подписью и не защищает от подмены архива вместе с контрольной суммой.

До установки изменений: проверить patch, миграции, сетевые обращения, зависимости и обработку секретов; затем резервная копия и управляемое обновление владельцем. Никакой автоматической публикации/GitHub Actions/deploy keys в пакете нет. Отзыв доступа к будущему репозиторию не удаляет скачанную копию кода у разработчика.
